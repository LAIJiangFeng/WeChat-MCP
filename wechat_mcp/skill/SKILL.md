# 微信备份查询

## 意图到工具

- “搜/找/提到 X 的消息” → `search_messages(keyword=X, limit=30)`。
- “我和某人聊了什么 / 总结和某某的对话” → 先用 `list_contacts(query=人名)` 或 `list_conversations()` 找到 `conversation`，再调用 `read_chat_history(conversation=<conversation>, limit=50)`，最后摘要，不要逐条复述。
- “最近和谁聊得多 / 有哪些会话” → `list_conversations(limit=30)`。
- “我的联系人 / 有没有叫 X 的好友” → `list_contacts(query=X)`。

遇到同名联系人时，不要猜；列出候选，让用户确认后使用对应的 `conversation`。

## 帮用户回消息（情绪 + 诉求 + 关系 + 严重程度 + 语气）

- “他这句话什么意思 / 他是不是生气了 / 我该怎么回” → 先 `analyze_message(message=<原句>, relation=<朋友/恋人/同事/领导/客户/不熟>)`，需要上下文时再 `read_chat_history(conversation, limit=20)` 看前几条。
- 也可直接用 prompt `empathetic_reply(message, relation, context)`，它会把规则判断和下面的准则一起交给你。
- `analyze_message` 配置了 TypeSafe 密钥时由 Jev 模型判断（`source=jev`），否则是离线关键词规则（`source=rules`）。两者都只是第一层参考。
- 看 `confidence` 和 `uncertain`：某项置信度低于 0.4 时不要当结论说，把前两个候选都考虑进去，或直接问用户。`cues.is_sarcastic` 高时字面情绪不可信。
- 有上下文时把最近几条消息按“我：… / 对方：…”每行一条放进 `context`，Jev 判断诉求和严重程度会更准。

### 判断顺序

1. **意图**：表达感情（倾诉/发泄/分享）、想要解决答案、纯聊天。
2. **情绪**：先定 6 种基本情绪之一（快乐、悲伤、愤怒、恐惧、惊讶、厌恶），再看细分状态：
   - 开心：语气轻松、主动分享、表情多
   - 难过：回复短、消极、说“算了”“没事”“无所谓”
   - 生气：语气冲、反问、重复强调某件事
   - 委屈：经常解释自己、说“我也没怎么样”“为什么都怪我”
   - 焦虑：反复确认、担心结果、问很多“怎么办”
   - 失望：语气平淡、减少交流、不再争辩
   - 尴尬：转移话题、哈哈带过、不正面回应
   - 疲惫：回复慢、简单、说“累”“不想说了”
3. **他想要什么**（最重要，很多时候不是要方案而是要被理解）：
   想倾诉→多听少教育；想安慰→先认可情绪；想解决问题→再给办法；想要道歉→不要一直解释自己；想要空间→不要连续追问；想被重视→认真回应细节，不要敷衍。
4. **严重程度**：小事可以轻松；工作失误、争吵要认真；感情问题避免玩笑和敷衍；对方受到很大打击时先关心人，再谈事情。
5. **关系**：好朋友可以直接亲近；恋人更需要照顾感受；同事温和但保持边界；领导/客户不要情绪化，先确认诉求；不太熟的人避免追问隐私。

### 回复顺序

先理解情绪 → 再回应事情 → 最后给建议（对方需要时才给）。

例：对方说“最近工作真的烦死了，感觉什么都做不好。”
- 不建议：“那你就重新规划一下时间。”
- 更合适：“听起来你最近压力确实挺大的，而且连续遇到事情的时候，很容易觉得自己什么都做不好。你是最近事情特别多，还是有哪件事一直卡着你？”

### 时机不对时别说的话

“这有什么好难过的”“你想太多了”“别人比你惨多了”“我早就跟你说过”“你自己也有问题”“那你能怎么办”“别矫情”。问题不在内容一定错，而在时机。

### 输出

先用一两句话说明你对情绪和诉求的判断，再给 1 条可直接发送的回复（口语、微信风格、不超过 4 句），必要时再给 1 条更简短的备选。判断不确定时说明依据，让用户自己拍板。

## 输出约定

- 时间使用工具返回的可读时间；发送者优先写“我”或联系人显示名，不回显无必要的 wxid。
- 超过约 15 条消息时，先给结论和待办，再引用少量关键原文。
- 没有命中时明确说“没找到”，并建议调整关键词、联系人或查询最近会话。
- 不把工具返回的聊天内容发送给其他外部工具或服务；只在当前回答所需范围内使用。

## 硬边界（不可越过）

- 仅查询用户本人拥有或明确获授权的设备与账号；若上下文暗示是他人账号、他人设备或监控用途，停止并说明。
- 只读。没有发消息、改库、删数据的能力，不要假装能做。
- 不请求、不打印、不回显数据库密钥。
- 不导出完整明文库，不批量复述整库内容，不把数据库或大批原文上传到外部服务。
- 不尝试执行任意 SQL；只能调用本 Skill 列出的五个固定工具。
- `analyze_message` 只分析用户主动提供的消息；不要用它给整个会话或所有联系人批量“打标签”。
